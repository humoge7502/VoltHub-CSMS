# VoltHub CSMS — Security & Architecture Audit

**Report ID:** VH-SEC-ARCH-2026-10-25
**Date:** 2026-10-25
**Target:** VoltHub CSMS monorepo (`apps/api`, `apps/worker`, `apps/web`, `db/oracle`, `db/timescale`, `infra`)
**Commit:** `ce9160e30cd106c45b6bdd1d8838b05dda860a49` (`main`, 2026-10-24) plus uncommitted working-tree changes
**Method:** Manual source review, schema review, configuration review, and targeted black-box reproduction against a local instance
**Findings:** 24 — 3 Critical, 7 High, 9 Medium, 5 Low
**Application source modified:** No. Only this report was added.

> **Release recommendation:** Do not expose this build to untrusted networks or real payment rails. AUD-01, AUD-02, AUD-03, AUD-05 and AUD-10 are release blockers: unauthenticated parties can read charger credentials, a fresh deployment ships with known production secrets, and an authenticated user can mint wallet balance without money or a chain transaction.

---

## 1. Executive Summary

VoltHub is an ambitious CSMS with a real domain model: OCPP 1.6J charging, reservations, time-of-use tariffs, invoices, an outbox to TimescaleDB, a worker relay, a carbon-aware controller, and a Next.js operator console. The code shows genuine care in several places — Argon2id password hashing with timing equalization, hashed and rotated refresh tokens, constant-time OCPP Basic authentication, `FOR UPDATE` locking on money rows, unique invoice constraints, and an ack-after-commit outbox.

The security posture does not yet match that ambition. The audit found **three Critical issues** that individually justify stopping a production launch:

1. **AUD-01 — Unauthenticated charger secret disclosure.** `GET /api/v1/stations/:id` is public and returns the full station row, including `auth_secret` and `ocpp_identity`. Any anonymous visitor can enumerate stations and obtain the exact Basic-auth password a charger uses on the OCPP endpoint. This was confirmed live: `/api/v1/stations/1` returned `auth_secret: "dev-VH-1-CP1"` and `ocpp_identity: "VH-1-CP1"`.
2. **AUD-02 — Production ships with development defaults.** The committed Compose stack publishes Oracle, TimescaleDB, the API, the web console and Grafana on `0.0.0.0` with fixed database passwords (`volthub_dev_pwd`), a fixed worker `INTERNAL_TOKEN`, and a Grafana datasource that embeds the Timescale password. The "prod" overlay requires `JWT_SECRET`/`INTERNAL_TOKEN` but explicitly leaves the database passwords and published ports untouched, and defaults Grafana to its built-in `admin/admin`. Internet exposure is a full-system compromise, not a configuration nit.
3. **AUD-03 — Wallet balance can be minted with an arbitrary signature.** Top-up settlement treats a self-signed EIP-191 authorisation from any linked wallet as payment. The message is generated by the server, but the signer is the account holder and no value moves: there is no on-chain transfer, no treasury receipt, no facilitator capture, and no tx-hash binding. A new account linked to a random ethers wallet settled three ₹10,000 intents and moved from ₹0 to ₹30,000. The receipt itself says `signed-authorisation (no gas, no chain write)`.

The High findings turn those cracks into a pattern. OCPP `StartTransaction` accepts any `idTag` of the form `TAG-<uid>` and maps it to a local user (`AUD-04`), so a leaked or guessed identity can start charging and bill a stranger. The API silently falls back to an in-memory store when Oracle is unreachable (`AUD-05`), which converts a database outage into a split-brain system that accepts writes and loses them on restart. Session list/detail endpoints do not consistently enforce station ownership (`AUD-06`), a malformed OCPP upgrade URI crashes the whole Node process (`AUD-07`), REST session start and OCPP `StartTransaction` have independent state machines that disagree (`AUD-08`), new sessions can select any historical or foreign tariff plan (`AUD-09`), and operator-created users receive `Temp@1234` with no forced reset (`AUD-10`).

The Medium and Low findings are the usual second-order effects: time-of-use windows are evaluated against a flat rate and in the wrong timezone (`AUD-11`); refresh tokens are hashed in memory but never written to Oracle, and the browser client never calls the refresh endpoint (`AUD-12`); invoice payment does not verify the payer against the session owner (`AUD-13`); station scoping fails open when `station_id` is absent (`AUD-14`); the outbox acknowledgement query over-matches with `LIKE` (`AUD-15`); `meterStop` can be recorded below the highest observed power (`AUD-16`); unbounded in-memory arrays and whole-file JSONL reads grow without limit (`AUD-17`); the architecture assumes a single API process (`AUD-18`); the audit ledger has no tamper evidence (`AUD-19`); tokens live in `localStorage` (`AUD-20`); OCPP energy samples without an explicit measurand are dropped (`AUD-21`); there is no retention or account-deletion path (`AUD-22`); metrics and verbose health are public (`AUD-23`); and wallet challenge verification trusts the `Origin` header (`AUD-24`).

**What is working.** The password and session primitives are better than typical for a project at this stage (Argon2id, dummy-hash comparison, HS256 algorithm pinning, refresh-token family revocation, constant-time OCPP Basic auth, 256 KB WebSocket payload cap, per-connection message rate limiting, transaction ownership checks, `FOR UPDATE` money locking, unique invoice numbers, meter-regression guards, connector-occupancy guards, and no `DELETE` grants on the ledger). The outbox design is also sound in principle: dedupe keys, ack-after-commit, poison isolation, and a measured lag gauge.

**Bottom line.** The domain thinking is ahead of the security engineering. The fastest path to a defensible launch is not a rewrite: fix the three Critical issues, close the OCPP identity and split-brain gaps, remove the in-memory fallback from production, force a password reset on provisioned accounts, and make station scope fail closed. Those eight changes remove most of the exploitable blast radius. The 30/60/90 plan in §7 sequences the rest.

- Third-party penetration testing of the payment provider or chain RPC.

- The AI service (`apps/ai`) except where it touches the audited API.
- Legal/compliance certification (DPDP, GDPR, PCI). Retention is assessed as an engineering control only.

### 2.3 Method

1. **Read the code paths, not the documentation.** Every finding cites the exact source line that implements the behaviour. Where docs and code disagree, the code is authoritative and the discrepancy is noted.
2. **Trace the money path end to end.** Wallet link → challenge → top-up intent → settlement → ledger → invoice → payment → outbox. Each transition was checked for authentication, authorization, idempotency, rounding, and durability.
3. **Trace the OCPP path end to end.** HTTP upgrade → Basic auth → `BootNotification` → `Authorize` → `StartTransaction` → `MeterValues` → `StopTransaction`, including disconnect and error paths.
4. **Reproduce what can be reproduced.** A local instance was started with the repository's own Compose defaults. Three behaviours were confirmed live: the station secret leak (AUD-01), wallet minting (AUD-03), and REST/OCPP session split-brain (AUD-08). A fourth, the OCPP `URIError` crash (AUD-07), was confirmed by driving the upgrade handler with a malformed path.
5. **Mark what could not be confirmed.** Hardware-dependent charger behaviour, multi-replica races, and runtime Oracle behaviour that requires a licensed instance are labelled `UNVERIFIED` rather than asserted.
6. **Score by operational priority, not CVSS alone.** CVSS 3.1 is provided for exploitable technical findings. Severity also accounts for blast radius and business impact; where the two diverge, the rationale is stated in the finding. AUD-03 is the clearest example: CVSS 6.5 because it requires an authenticated account, Critical because it is direct, repeatable theft from the money rail.

### 2.4 Evidence standard

- `file:line` references point at the current working tree at the commit above.
- "Confirmed" means observed in a running instance or directly in executed code.
- "Code-verified" means the behaviour follows unambiguously from the cited lines but was not exercised at runtime.
- `UNVERIFIED` means the behaviour depends on an environment, hardware, or deployment topology not available during the audit.

## 5. Detailed Findings

### AUD-01 — Public station endpoint discloses charge-point OCPP credentials

**Severity:** Critical
**CVSS 3.1:** 9.1 — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N`
**Location:** `apps/api/src/routes.js:295-311`; the charge-point spread is at `:303`, returned under `station.charge_points` at `:320`
**Status:** Confirmed at runtime against the repository's Compose stack.

**What happens.** `GET /api/v1/stations/:id` is mounted without `authRequired`. It loads every charge point for the station and returns `...c` — the entire internal row — to the caller. That row contains `ocpp_identity` and `auth_secret`, the two values required to authenticate to the OCPP WebSocket as that charger. The station object itself is also spread (`...s`), so any future secret added to the station row would leak the same way. There is no public/private DTO boundary.

**Attack / repro.**

1. `curl -s http://localhost:4000/api/v1/stations/1`
2. Read `station.charge_points[].ocpp_identity` and `.auth_secret`. The observed response contained `"ocpp_identity":"VH-1-CP1"` and `"auth_secret":"dev-VH-1-CP1"`.
3. Open `ws://localhost:4000/ocpp/VH-1-CP1` with `Authorization: Basic base64("VH-1-CP1:dev-VH-1-CP1")`.
4. Send `BootNotification`, then `StartTransaction` with an `idTag` of `TAG-<victim_uid>` (AUD-04). The session is billed to the victim while the attacker controls the charging session.

The same response also exposes `last_seen_at`, firmware/model metadata, connector state, and `cp_id`, which makes the estate enumerable without authentication.

**Expected vs actual.**

- Expected: a public station DTO containing name, location, status, connector availability, price, and amenities. OCPP credentials never cross the public boundary.
- Actual: full charge-point rows, including the Basic-auth password and OCPP identity, are returned to anonymous callers.

**Impact.** An attacker can impersonate any charger whose station ID they can enumerate (IDs are sequential), inject meter values, change connector state, start or stop transactions, and — combined with AUD-04 — bill arbitrary users. Rotating a leaked secret does not help until the endpoint stops returning it. This is a direct path from an anonymous HTTP request to control of the physical charging estate.

**Fix.** Replace the spread with an explicit allow-list projection; keep `auth_secret` server-side only; add a regression test that asserts the key is absent; rotate every secret that has been exposed; add a separate `/stations/:id/public` contract if the UI needs more fields. **Effort:** 2 h. **Depends on:** secret rotation runbook. **Timeline:** Now, before any network exposure.

### AUD-02 — Production Compose ships development credentials and publishes data ports

**Severity:** Critical
**CVSS 3.1:** 9.8 — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
**Location:** `infra/docker-compose.yml:7,9,13,34,35,56,63,89,93,125,166,186`; `infra/docker-compose.prod.yml:15-17,23-30`; `infra/grafana/provisioning/datasources/timescale.yml:6-7`
**Status:** Code-verified; the defaults are literal in the committed files.

**What happens.** The base Compose file is the documented one-command stack. It creates Oracle and Timescale with the password `volthub_dev_pwd`, connects the API and worker with the same literal, publishes Oracle `1521`, Timescale `5432`, the API `4000`, the web console `3000`, and Grafana `3001` on `${BIND_ADDR:-0.0.0.0}`, seeds the demo profile, and gives the worker `INTERNAL_TOKEN: dev-internal`. The production overlay requires strong `JWT_SECRET`, `INTERNAL_TOKEN`, and `AI_TOKEN`, but its own header says: "Database passwords are still the base file's values." It does not remove the published ports, does not change the Oracle/Timescale credentials, and does not set a Grafana admin password. The Grafana datasource embeds the Timescale password in plaintext.

**Attack / repro.**

1. From any host that can reach the deployment: `sqlplus volthub/volthub_dev_pwd@<host>:1521/freepdb1`.
2. Or `psql postgresql://volthub:volthub_dev_pwd@<host>:5432/volthub`.
3. Or open `http://<host>:3001` and log in with Grafana's built-in `admin/admin` (the stack sets no `GF_SECURITY_ADMIN_PASSWORD`).
4. Read `app_user.password_hash`, `wallet_account`, `wallet_ledger`, `invoice`, `audit_log`; write invoices, sessions, and ledger rows as the schema owner. Bypass the API entirely on port 4000, including its TLS terminator and rate limits.

The Oracle healthcheck at `:21` also embeds the password, so it is visible in `docker inspect` and process listings.

**Expected vs actual.**

- Expected: production uses generated secrets from a secret manager or `.env` that is never committed; database ports are not published; Grafana is not exposed or requires a strong unique admin password; demo seed is off; the API is reachable only through the TLS proxy.
- Actual: known passwords, published data ports, demo seed, and default Grafana credentials survive the production overlay.

**Impact.** Full confidentiality, integrity, and availability compromise of the CSMS and its telemetry. An attacker can read every user and charger record, alter wallet balances and invoices, delete or forge audit history (as owner), and pivot to the host. This is the highest-blast-radius finding in the report and the easiest to exploit.

**Fix.** Add a production Compose file that sets `ORACLE_PASSWORD`, `APP_USER_PASSWORD`, `POSTGRES_PASSWORD`, `TS_PASSWORD`, and `GF_SECURITY_ADMIN_PASSWORD` from required variables; remove all `ports:` for Oracle/Timescale (use the internal network); bind the API/web to `127.0.0.1` behind the proxy; set `SEED_PROFILE=empty` and `OCPP_AUTH=require`; remove the password from the Grafana datasource (use a secret or env interpolation); rotate every credential; add a `docker compose config` test that fails on known defaults. **Effort:** 8 h. **Depends on:** deployment topology decision. **Timeline:** Now.

### AUD-03 — Wallet top-up mints balance from an unverified client signature

**Severity:** Critical
**CVSS 3.1:** 6.5 — `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`
**Location:** `apps/api/src/db/store.js:706-751`; `apps/api/src/wallet/rail.js:8-12,63-76,95-104`; routes at `apps/api/src/extended.js:111-134`
**Status:** Confirmed at runtime against a fresh local user.

**What happens.** The wallet rail is an EIP-191 `personal_sign` authorisation. `createTopupIntent` builds a server-side message naming the intent, the linked wallet, the INR amount, the wei equivalent, the chain ID, and an expiry. `settleTopup` verifies that the signature recovers to the linked address, then calls `topup()` and credits the ledger. The signature proves only that the user controls the address. It does not prove that any ETH moved, that the treasury received anything, or that the "amount" is backed by a funded source. There is no transaction hash, no on-chain receipt, no facilitator call, and no uniqueness constraint against a real transfer. The receipt is explicit: `mode: 'signed-authorisation (no gas, no chain write)'`.

**Attack / repro.**

1. Register a normal account.
2. `POST /api/v1/me/wallet/challenge` with a freshly generated ethers wallet address, sign the challenge, and `POST /me/wallet/link`.
3. `POST /api/v1/me/wallet/intent` with `{ "amount": 10000 }`; sign the returned message with the same wallet.
4. `POST /api/v1/me/wallet/settle` with the intent id and signature. The wallet is credited ₹10,000.
5. Repeat steps 3–4. Each intent is new, so the per-intent replay guard does not apply.

Observed in the running instance: a new user linked a random wallet and settled three ₹10,000 intents; the balance moved `0 → 10,000 → 20,000 → 30,000`, and each receipt carried `mode: "signed-authorisation (no gas, no chain write)"`. The `wallet-intent:<id>` mutex correctly prevents double-settling one intent, but it does not constrain the number of intents.

**Expected vs actual.**

- Expected: credit is posted only after a confirmed on-chain transfer to a VoltHub treasury address (or a payment-processor capture), with the tx hash as an idempotency key, a minimum confirmation count, and amount/recipient binding.
- Actual: a self-signed message is treated as payment. The user is both payer and payee, and no value enters the system.

**Impact.** Any authenticated user can create unbacked prepaid balance up to ₹10,000 per intent, without limit, and spend it on charging sessions and invoices. There is no withdrawal endpoint in the tree, so the direct cash-out path is absent, but the operator loses real energy revenue and the ledger, invoices, and revenue reports become fiction. If the rail is presented to users as a real top-up, this is also a consumer-protection issue. The code and docs are honest that this is a demo rail; the defect is deploying a demo rail as the production money path.

**Fix.** Choose one: (a) disable the signed rail in production and boot-fail if `WALLET_RAIL` is not `onchain`; (b) implement treasury-address verification — parse the tx, check `to`, `value`, `chain_id`, confirmations, and a unique `tx_hash`, and credit only after confirmation; (c) integrate a payment processor with server-side capture. Add a per-user daily cap and a reconciliation job regardless. **Effort:** 24 h. **Depends on:** payment/treasury decision and RPC provider. **Timeline:** Now (disable) / 30 days (real rail).

### AUD-04 — OCPP authorizes any `TAG-<uid>` as that user

**Severity:** High
**CVSS 3.1:** 6.5 — `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`
**Location:** `apps/api/src/ocpp/gateway.js:494-524`; `apps/api/src/routes.js:600-626`; default tag at `apps/api/src/routes.js:499`
**Status:** Code-verified; exercised indirectly in the split-brain repro.

**What happens.** Both `Authorize` and `StartTransaction` parse the `idTag` with `/^TAG-(\d+)$/` and treat the captured number as the user ID. `Authorize` returns `Accepted` if `store.users.has(n)`. `StartTransaction` calls `store.startSession({ uid: n, idTag: p.idTag, ... })`, so the session is billed to user `n`. ### AUD-05 — Silent in-memory fallback accepts writes during a database outage

**Severity:** High
**CVSS 3.1:** 7.4 — `AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:H/A:H`

**Status:** Code-verified; the fallback branch is explicit and unconditional.

**What happens.** When `ORACLE_HOST` is set, the API attempts `upgradeStore()` before binding the port. ### AUD-08 — REST session start and OCPP `StartTransaction` split-brain the connector

**Severity:** High
**CVSS 3.1:** Not scored — business-logic integrity and availability, no single-shot confidentiality impact.
**Location:** `apps/api/src/routes.js:473-506`; `apps/api/src/db/store.js:912-971`; `apps/api/src/ocpp/gateway.js:501-536`
**Status:** Confirmed at runtime.

**What happens.** `POST /api/v1/sessions/start` calls `store.startSession()` directly. That function checks the connector is `AVAILABLE` or `RESERVED`, creates a `PREPARING` session with `start_meter_kwh` from the request (0 if absent), and sets the connector to `OCCUPIED` under the `conn:<cp>:<no>` mutex. It does not send anything to the charger. When the charger later sends OCPP `StartTransaction` for the same connector, the gateway calls the same `startSession()`, which sees `OCCUPIED` and rejects with `NOT_BOOKABLE`. The gateway returns a CALLERROR `InternalError`, so the charger never receives a `transactionId` and cannot charge. The reverse order is also broken: if OCPP starts first, the REST call gets a 409.

**Attack / repro.**

1. As a driver, `POST /api/v1/sessions/start` with `{ "cpId": 1, "connectorNo": 1, "planId": 2 }`. Response: `201`, session `61`, `start_meter_kwh: 0`, connector `OCCUPIED`.
2. Connect as the charger and send `StartTransaction` for connector 1 with a valid tag. Response: `[4, "probe-1", "InternalError", "NOT_BOOKABLE: connector 1:1 is OCCUPIED", {}]`.
3. The connector remains occupied by a session the charger does not know about. No energy flows; the driver sees a stuck session; the operator sees a phantom.
4. A driver can repeat step 1 across connectors to occupy the estate without charging (availability abuse).

**Expected vs actual.**

- Expected: one state machine. The app requests a remote start, the charger confirms with `StartTransaction`, and only then does the connector become `OCCUPIED` and the session become `CHARGING`. The REST call should return `202` with a pending correlation id, or the OCPP transaction should adopt a pre-created pending row idempotently.

**Impact.** The primary driver flow fails against real hardware; connectors get stuck; sessions are billed from a zero meter start; operators must manually reconcile. It is also a cheap availability attack for any authenticated driver. The `start_meter_kwh: 0` default means a later stop can bill the charger's entire lifetime register as delivered energy if the charger's `meterStart` is ignored (see AUD-16).

**Fix.** Introduce `PENDING_START` with a TTL: REST creates a pending intent (not an occupied connector), sends `RemoteStartTransaction`, and returns `202`; OCPP `StartTransaction` atomically adopts the pending row for that connector/tag, sets `start_meter_kwh` from `meterStart`, and transitions to `PREPARING`. Add an idempotency key per `(connector, idTag, request)`. If OCPP does not confirm within the TTL, expire the pending row and leave the connector `AVAILABLE`. **Effort:** 16 h. **Depends on:** OCPP command correlation (AUD-18 for multi-replica). **Timeline:** 2 weeks.

### AUD-15 — Outbox acknowledgement over-matches session events with `LIKE`

**Severity:** Medium
**CVSS 3.1:** 4.2 — `AV:N/AC:H/PR:L/UI:N/S:U/C:N/I:L/A:L`
**Location:** `apps/api/src/routes.js:1123-1139`
**Status:** Code-verified.

**What happens.** The durable outbox ack path updates rows by exact `event_id` and exact `dedupe_key`, then adds a special case for session transitions. Because the Oracle package's key includes a wall-clock suffix and the API's copy uses `Date.now()`, the code builds `sess:<session>:<STATE>:%` and runs `dedupe_key LIKE :p`. That pattern matches every transition for the same session and state, not just the event being acknowledged. If a session goes `CHARGING → SUSPENDED → CHARGING`, the first `CHARGING` ack also marks the second `CHARGING` row `processed_at`, even though the worker has not relayed it. The worker's next poll skips it, so Timescale never sees the resume.

**Attack / repro.**

1. Let a session transition to `CHARGING`, then `SUSPENDED`, then `CHARGING` again.
2. The worker polls the first batch and acks the first `CHARGING` event.
3. `markDurableProcessed` executes `UPDATE ... WHERE dedupe_key LIKE 'sess:61:CHARGING:%'`, which matches both `CHARGING` rows.
4. The second `CHARGING` row is marked processed; the relay never sends it. Timescale's connector-state history shows a suspend with no resume.

**Expected vs actual.**

- Expected: acknowledge exactly the event(s) returned by the poll, by primary key or full dedupe key. If the key must be normalized, store a stable `event_key` at emit time and ack that.
- Actual: a prefix `LIKE` acknowledges future rows with the same session and state.

**Impact.** Silent gaps in telemetry and state history, which feed dashboards, carbon accounting, and dispute evidence. It is not a direct money bug, but it corrupts the audit trail that is supposed to prove what happened. Repeated suspend/resume cycles make the gap more likely.

**Fix.** Add a stable `event_key` column (or use `event_id` only); ack by exact key; if the two engines must reconcile, normalize the key at write time, not at ack time. Remove the `LIKE` branch and add a test with two same-state transitions. **Effort:** 2 h. **Depends on:** schema migration. **Timeline:** 30 days.

### AUD-16 — `meterStop` can be recorded below the session's peak register

**Severity:** Medium
**CVSS 3.1:** 4.9 — `AV:N/AC:L/PR:H/UI:N/S:U/C:N/I:H/A:N`
**Location:** `apps/api/src/db/store.js:1128-1151`; `db/oracle/V011__stop_meter.sql:129-145`
**Status:** Code-verified.

**What happens.** `stopSession(sid, reason, endMeterKwh)` computes `peak` from `_maxMeter` (the highest register seen in `MeterValues`). If the caller supplies an explicit `endMeterKwh`, the function uses it as long as it is finite, non-negative, and not below `start`. It never compares `end` with `peak`. A charger that reports a stop register below an earlier meter value — a firmware bug, a register reset, or a malicious charger — is accepted. Billing then computes `end - start`, undercounting delivered energy. The same logic exists in `V011`'s stop path.

**Attack / repro.**

1. Connect a charger (or simulator) with a valid secret.
2. Send `MeterValues` with a register of 50 kWh.
3. Send `StopTransaction` with `meterStop: 20 kWh` (above start 0, below peak 50).
4. `stopSession` accepts 20; the invoice bills 20 kWh, not 50.
5. Repeat across sessions for systematic revenue loss.

**Expected vs actual.**

- Expected: `meterStop` must be monotonic with respect to all observed registers; use `max(peak, end)` or reject the stop with `METER_REGRESSION` and raise a fault. A register reset should be handled explicitly (new register epoch), not silently accepted.
- Actual: any value at or above `start` is trusted, even if it contradicts the meter history.

**Impact.** Under-billing and meter-integrity loss. A malicious or faulty charger can erase up to the entire session's energy from the bill while leaving plausible readings. It also weakens dispute evidence: the invoice's end register conflicts with the stored `MeterValues`, and nothing flags it.

**Fix.** Reject `end < peak` (or clamp to `peak` and raise a `METER_REGRESSION` fault), persist the peak and the source of the stop value, and add a reconciliation check that flags any session whose `end_meter_kwh` is below `max(reading.meter_kwh)`. Apply the same rule in `V011`. **Effort:** 4 h. **Depends on:** none. **Timeline:** 30 days.

### AUD-18 — The architecture assumes a single API process

**Severity:** Medium
**CVSS 3.1:** Not scored — architectural scalability and correctness risk.
**Location:** `apps/api/src/db/store.js:42-60,236`; `apps/api/src/ocpp/gateway.js:309`; `apps/api/src/server.js:143`
**Status:** Code-verified by design inspection.

**What happens.** The store's `Mutex` is an in-process `Map` of promise chains. The OCPP registry is a `Map` local to `mountOcpp`. The rate limiters, the outbox queue, the refresh-token map, and the sweeper are all process-local. The session/wallet uniqueness checks run inside the local mutex, not a database lock. The Compose stack runs one API container, so this works today. Scale it to two replicas and the invariants break: both replicas can pass the `AVAILABLE` connector check and create a session; both can settle the same wallet intent if the intent is visible to both (the mutex does not cross processes); a charger can connect to both replicas because each registry accepts the same identity; OCPP `RemoteStart` sent from replica A cannot reach a charger connected to replica B; and `/health` reports only the local view.

**Attack / repro.**

1. Run two API replicas behind a load balancer, both connected to the same Oracle.
2. Send two concurrent `POST /sessions/start` for the same connector; each replica's local mutex serializes only its own request, so both can insert a session before either sees the other's `OCCUPIED` state.
3. Connect the same charger identity to both replicas; both accept and both send commands.
4. Settle one wallet intent through both replicas concurrently; the local `SETTLED` check is not shared, and the only backstop is a database constraint (if present).

**Expected vs actual.**

- Expected: cross-process coordination via database row locks/unique constraints for money and occupancy, a shared OCPP presence/registry (Redis pub/sub or sticky routing), distributed rate limits, and a single leader for sweeps.

The system cannot be made highly available without breaking its core invariants. This is a Medium today because the deployment is single-process; it becomes Critical the moment someone scales it.

**Fix.** Move occupancy and wallet transitions to `SELECT ... FOR UPDATE` / unique constraints in Oracle; add a distributed lock for OCPP commands; use sticky sessions or a shared registry for charger sockets; make the sweeper a singleton (DB advisory lock); document and enforce the single-replica constraint until then. **Effort:** 40 h. **Depends on:** Redis or Oracle AQ/coordination decision. **Timeline:** 90 days.

### AUD-19 — Audit ledger has no tamper evidence and runs as the schema owner

**Severity:** Medium
**CVSS 3.1:** 5.3 — `AV:N/AC:H/PR:L/UI:N/S:U/C:N/I:H/A:N`
**Location:** `db/oracle/V001__core_schema.sql:314-326`; `db/oracle/V004__triggers_grants.sql:37-41,93-95`; `db/oracle/V003__packages.sql:62-71`; `apps/api/src/db/oracle.js:27-28`
**Status:** Code-verified.

**What happens.** `audit_log` is a plain table: `audit_id`, actor, entity, action, old/new CLOB, timestamp. The migration creates a least-privilege `volthub_app_role` only if `CREATE ROLE` succeeds; on the documented `gvenzl` install it does not, and the migration prints "role layer skipped (owner-account app)". ### AUD-21 — OCPP `MeterValues` without an explicit measurand are silently dropped

### AUD-24 — Wallet challenge verification trusts the `Origin` header

**Severity:** Low
**CVSS 3.1:** 3.5 — `AV:N/AC:L/PR:L/UI:R/S:U/C:L/I:N/A:N`
**Location:** `apps/api/src/extended.js:38-47,67-79`
**Status:** Code-verified; real-wallet display behaviour is `UNVERIFIED`.

**What happens.** `originOf(req)` takes the request's `Origin` header (or the first `WEB_ORIGIN` entry), parses it, and uses its host/URI in the EIP-4361 challenge. There is no allow-list check against the configured production origin. A caller can request a challenge with `Origin: https://evil.example` and receive a message whose `domain` and `URI` name `evil.example`. The challenge is single-use and bound to the authenticated user, so an attacker cannot link a victim's wallet without a signature. But the signed message's provenance fields are attacker-controlled, which undermines the phishing-resistance EIP-4361 is supposed to provide: a wallet may display `evil.example` while the user believes they are linking to VoltHub, or the mismatch may be hidden by a wallet that only shows the statement.

**Attack / repro.**

1. As an authenticated user on a phishing page, the page calls `POST /api/v1/me/wallet/challenge` with `Origin: https://evil.example` (the browser sets this automatically for the attacker's origin).
2. The API returns a challenge with `domain: evil.example`, `URI: https://evil.example`.
3. The page asks the user to sign "to link your wallet to VoltHub"; the message text says VoltHub, but the domain field says evil.example.
4. The user signs; the page relays the signature to the real API with the victim's bearer token. The wallet is linked to the victim's account (the attacker still needs the victim's authenticated session, so this is primarily phishing/social engineering, not standalone takeover).

**Expected vs actual.**

- Expected: the server ignores the request `Origin` for message construction and uses a configured canonical origin; it validates `Origin` against an allow-list and rejects unknown origins; the challenge binds the user, the action, and a server-side nonce, and the UI displays the canonical domain.
- Actual: the message's domain/URI are whatever the caller sends.

**Impact.** Phishing and signature-provenance confusion; weakened EIP-4361 guarantees; possible reputational harm if a signature is later presented as consent from a different origin. The direct account-takeover path is blocked by the authenticated challenge and single-use nonce, hence Low.

**Fix.** Use `WEB_ORIGIN` (server configuration) for the challenge, never the request `Origin`; if multiple origins are supported, allow-list them and reject others; bind `domain`/`uri` into the signed message and verify them; add a UI warning when the connected origin differs. **Effort:** 2 h. **Depends on:** deployment origin list. **Timeline:** 30 days.

## 6. Five Strengths Worth Keeping

1. **Password hashing is done properly.** New passwords use Argon2id with `m=19456, t=2, p=1` (`apps/api/src/db/store.js:66-70,81-82`); the login path compares against a dummy hash for unknown users to equalize timing (`store.js:1928`), and legacy scrypt hashes are verified only through the legacy branch. This is better than most early-stage codebases and should not be regressed while fixing AUD-10.
2. **JWT and refresh primitives are pinned and rotated.** Access tokens are HS256-only and verified with `algorithms: ['HS256']` at every site (`middleware/auth.js:136`, `middleware/security.js:90`); refresh tokens are random 32-byte values stored as SHA-256 hashes, rotated on use, grouped into families, and a reused revoked token burns the family (`auth.js:68-107`). The httpOnly/SameSite cookie helper is also correct (`auth.js:112-119`). The gap is persistence and client use (AUD-12), not the primitive.
3. **OCPP transport hardening is real.** Basic auth uses a length check plus `crypto.timingSafeEqual` (`ocpp/gateway.js:300-306`); the WebSocket server caps payloads at 256 KB (`server.js:126-129`); the gateway enforces a per-connection message rate and rejects non-allow-listed frames; `MeterValues` verifies that the transaction belongs to the connected charge point (`gateway.js:552-559`); and duplicate identities close the stale socket (`gateway.js:347-353`). These controls are why AUD-07 is a crash rather than a memory-exhaustion disaster.
4. **The Oracle money path uses real database invariants.** `billing_pkg.bill_session` locks the session `FOR UPDATE` and rejects double billing (`V003:380-386`); `pay_invoice` locks the invoice and wallet (`V003:410-414`); invoice numbers are unique; `V011` adds meter-regression checks; `V004`'s connector guard blocks direct `connector.status` updates and the grant set has no `DELETE` on ledger/audit/readings (`V004:82-83`). The missing piece is owner binding (AUD-13) and tamper evidence (AUD-19), not the locking discipline.
5. **The outbox is designed like a real relay.** Events carry a unique `dedupe_key` (`V001:329-336`), the worker acks only after the Timescale `COPY` commits (`apps/worker/src/index.js:117-122`), poison events are quarantined instead of blocking the queue, the API bounds the queue with soft/hard caps and retention (`store.js:294-325`), and lag is measured rather than asserted (`store.js:327-345`; `/health` and `/metrics` expose it). AUD-15 is a narrow ack bug in an otherwise sound design.

## 10. CVSS Method and Scoring Notes

- **Standard:** CVSS 3.1 base score, as defined by FIRST. No temporal or environmental metrics are applied; the score is a reproducible baseline, not a risk rating.
- **Scope:** `S:U` unless a finding crosses a security authority. No finding required `S:C`; tenant isolation is an authorization failure within the same authority, and the money rail is a business-logic failure, not a sandbox escape.
- **Severity vs score:** severity is operational priority. It combines the CVSS score with blast radius, exploitability, and business impact. AUD-03 is the clearest divergence: CVSS 6.5 because it needs an authenticated account, but Critical because it is repeatable, direct theft from the money rail. AUD-14 is Medium at 6.8 because the fail-open needs an orphaned CP row; the impact is high but the precondition is uncommon.
