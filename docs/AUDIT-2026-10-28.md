# VoltHub CSMS — cross-domain audit and the path to production-grade

**Date:** 2026-10-28 · **Scope:** whole repository · **Method:** seven domain specialists
(security, architecture, data, accessibility, test engineering, production readiness,
payments) each read the code, then the highest-severity claims were re-verified by hand
against the source. Evidence below is file:line, not opinion.

This document supersedes the defect list in `docs/STRATEGY-AND-ROADMAP.md` §2 where they
disagree; that catalogue is still accurate on everything it marks closed.

---

## Verdict

The architecture is not the problem. The two-engine split, the in-transaction outbox, the
store port, the OCPP gateway — these are better than what most commercial CSMS codebases
look like. What holds the project back is that **the deployed artifact is not the hardened
artifact**: the code contains production guards, and the deployment path bypasses every
one of them. Second to that, the money rail has correctness holes that a demo never
exercises and a paying customer always would.

Fix two things — run the demo with the production overlay, and make wallet writes
transactional — and this stops being a portfolio project and starts being a system you
could put 50 connectors on.

---

## 1. The one finding that matters most

**The public deployment runs in dev mode, so three "production-only" guards never arm.**

`scripts/share-demo.sh:26` builds the stack from `infra/docker-compose.yml` alone. That
file never sets `NODE_ENV` (verified: `grep NODE_ENV infra/docker-compose.yml` → nothing).
`infra/docker-compose.prod.yml` is the overlay that sets `NODE_ENV: production` — and the
demo script does not use it. Three separate guards key off that variable:

| Guard                  | Code                                                                                            | What it does in the live demo                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Unsigned wallet top-up | `apps/api/src/routes.js:201-203` — `NODE_ENV !== 'production' && WALLET_UNSIGNED_TOPUP !== '0'` | **On.** Any authenticated user credits their own wallet, ₹10,000 per request, no signature                                             |
| OCPP `dev-` secrets    | `apps/api/src/ocpp/gateway.js:283` — rejected only `if (prod && /^dev-/)`                       | **Accepted.** Every seeded charge point authenticates with `dev-<identity>`, and the identity is published by an unauthenticated route |
| `/internal/*` token    | `apps/api/src/routes.js:1112-1115` — falls back to the published `dev-internal`                 | **Accepted.** Anyone can ack telemetry out of the outbox or expire reservations                                                        |

Each of these is correctly written. Each is correctly tested. All three are inert in the
only environment that is publicly reachable. This is the difference between "we fixed
SEC-050" and "the thing on the internet is safe", and it is a deployment bug, not a
security-design bug — which is why the earlier passes missed it: they verified against
`NODE_ENV=production` and against unit tests, never against the live container's env.

**Fix (hours, not days):** make `share-demo.sh` use
`-f infra/docker-compose.yml -f infra/docker-compose.prod.yml`, set `NODE_ENV` explicitly
in the base compose, and make the API **refuse to boot** when `NODE_ENV` is unset rather
than assuming development. Fail closed, once, at the only place that can be forgotten.

## 3. By domain

### 3.1 Money — the rail can mint, lose, and double-count

The signature ceremony is well designed (domain separation, amount binding, nonce
storage, replay refusal) and it authorises **intent**, not **funding**. Nothing in the
system ever captures money from a payer: `settleTopup` goes straight to `topup()`. With
the unsigned path live (§1) that means unlimited self-credit; even with it closed, a
valid signature from a user with no funds still credits the wallet. There is no PSP/UPI
capture, no velocity cap, no `funding_ref` on a credit.

Beyond that: `wallet_ledger` is missing from `MIRROR_SEQ_TABLES` (`oracle.js:629`) so a
top-up can 500 and lose the credit; `seq_no = count()+1` (`store.js:551`) collides on
`(user_id, seq_no)` under concurrency; there are no refunds, credit notes or disputes
(`REFUND` is declared in `V001:77` and never written); invoices have no gapless FY serial,
no GSTIN, no place of supply, no CGST/SGST lines — none of which a real Indian charging
operator can trade without. Reconciliation exists only as a CI invariant, never at
runtime, so drift is invisible until someone reconciles by hand.

**This is the domain where "working project" and "strongest project" diverge most.**

### 3.2 Security — good design, one deployment away from being armed

After §1, the remaining exposure is structural rather than accidental: DB ports published
on `0.0.0.0` with dev passwords (`infra/docker-compose.yml:7,9,13`), operator and driver
credentials seeded with real Argon2id hashes and printed by the demo script, and a
`GET /stations/:id/connectors/live` route that publishes `ocpp_identity` to anonymous
callers. The access token still lives in `localStorage` (15-minute window; the refresh
cookie is already httpOnly — the residual risk is small and correctly scoped in ISS-04).

### 3.3 Data & schema

The two strongest structural gaps: no tenant column anywhere (ADR-0009 describes
multi-tenancy; the schema has zero `tenant_id` and no VPD/RLS), and no migration ledger.
The outbox has no `FOR UPDATE SKIP LOCKED` claim query at all — it is an in-memory array
filtered per request — and no purge of processed rows, so the table is unbounded by
design. Chunk intervals and retention are sensible; cagg correctness is not (§2 #11).

### 3.4 Scale & architecture

The store port is bypassed by the OCPP gateway: connector status, CP status, faults and
state events are mutated straight into the process cache (`gateway.js:345-480`) with no
adapter method, so after a restart a connector mid-session re-hydrates as `AVAILABLE` and
becomes bookable. A second API instance breaks three ways (in-memory OCPP registry,
in-memory outbox ack, refresh tokens never written to Oracle). None of this matters at one
instance; all of it blocks the first horizontal scale-out.

### 3.5 Console

The console is visually strong and increasingly well-instrumented, but it is an
operator's tool that cannot yet answer "what is broken right now" at fleet scale: the
dashboard is single-station behind a dropdown, faults cap at five with no "of N", and
every list page that matters is a one-shot fetch. The a11y work is real but inverted in
one place — the loudest live region is the one nobody needs announced, and the quiet one
is the KPI strip.

### 3.6 Operations

Nothing scrapes `/metrics`; nothing alerts; nothing backs up; nothing pins a deploy
digest. `share-demo.sh` rebuilds from whatever is on disk and force-recreates, so
"rollback" means `git revert` plus a ten-minute rebuild. The load test proves almost
nothing (50 VUs on two routes, no OCPP socket, no relay, and its lag assertion compares a
count to a millisecond threshold).

### 3.7 Tests & CI

189 cases is a real suite, and the OpenAPI drift gate is genuinely good. The weak spots
are the ones that matter: the Oracle invariant job fails open, the authz surface is
sampled rather than enumerated, the "durable tier" test is a scripted fake that asserts
SQL text, and nothing blocks on coverage or performance. Several tests are order-dependent
(shared ports 4105/4107, a module-global pool seam rewritten 10×).

## 4. What is already strong — do not regress it

- The outbox pattern itself: one transaction boundary, at-least-once relay, idempotent
  sink on `(session_id, ts)`. This is the right design and it is correctly implemented.
- The store port and `local` test double: hermetic tests that run in seconds.
- Error bands as a single contract between PL/SQL and HTTP.
- The OpenAPI drift gate (`scripts/gen-openapi.js --check`) — most teams never build this.
- 18 ADRs that explain _why_, not just _what_.
- The console's design system and the documentation density around it.
- SEC-050's sentinel-and-provision model for credentials — once §1 arms it.

## 5. Sequenced plan

Ordered so that each step removes a class of risk rather than a symptom. Effort is
engineering time, not calendar time.

### Sprint 1 — make the live thing safe (3–4 days)

1. Production overlay in the deploy path + boot-refuse when `NODE_ENV` is unset (§1).
2. Unpublish DB ports in the prod overlay; `${VAR:?}` for every password.
3. Sentinel the operator/driver seed rows; stop printing credentials from `share-demo.sh`.
4. `GET /sessions` tenancy scoping; drop `ocpp_identity` from the public connector route.
5. Trivy `exit-code: 1`; pin action SHAs.

**Done when:** a fresh `share-demo.sh` deploy rejects unsigned top-up, rejects `dev-`
OCPP secrets, rejects `dev-internal`, and an anonymous caller cannot reach Oracle.

### Sprint 2 — make the money path correct (1.5–2 weeks)

6. Top-up moves into a PL/SQL package: `FOR UPDATE`, relative balance update, DB
   sequence, unique idempotency key on intent id (§2 #2).
7. One idempotency middleware, applied to every money-bearing POST (§2 #8).
8. Session lifecycle: hold funds at start, refuse below threshold, sweep and bill stale
   sessions, close on OCPP disconnect, dunning on `DUE` (§2 #10).
9. Runtime reconciliation job + alert on any non-zero drift row.
10. GST-compliant invoice: gapless per-FY serial, tax lines, credit notes, retention.

**Done when:** `sum(wallet_ledger) == wallet_account.balance` holds under a concurrent
top-up + invoice-payment test, and a killed OCPP connection leaves no session `CHARGING`.

### Sprint 3 — make it operable (1–2 weeks)

11. Backup + PITR + a restore drill that is actually run (§2 #4).
12. Prometheus + alert rules + `/health/deep` blackbox probe (§2 #14).
13. Migration ledger, idempotent DDL, per-file savepoints (§2 #15).
14. Bounded outbox hydration + `FOR UPDATE SKIP LOCKED` claim + purge (§2 #3).
15. OCPP ping/pong watchdog (§2 #9); UTC everywhere (§2 #5).
16. Digest-pinned images, N-1 rollback, and a load test that includes OCPP and the relay.

**Done when:** you can restore yesterday's billing database into a scratch environment in
under an hour, and an alert fires when the relay stops draining.

### Sprint 4 — make it grow (quarter)

17. Store-port coverage for connector/CP/fault state, so a restart cannot resurrect a
    bookable mid-session connector (§3.4).
18. Multi-tenancy: `tenant_id` + Oracle VPD, or a documented decision to stay
    single-tenant.
19. Second-instance readiness: shared OCPP registry, Oracle-side ack, refresh tokens
    persisted.
20. TypeScript on the console (ISS-16), cagg correctness fix, coverage floor in CI.

## 6. Definition of "strongest working project"

Not "no open issues". Concretely:

- A stranger can clone it, run one command, and get a stack that refuses default
  credentials.
- Every rupee that enters the wallet is traceable to a funding event, and
  `ledger == balance` is enforced at runtime, not in CI.
- Killing any single container at any moment loses no billing row and no telemetry tick.
- An operator can answer "what is broken right now, and since when" in one screen.
- A restore has been performed, timed, and written down.
- The suite fails when the money path is wrong — including when Oracle is unreachable.
